API do EvoCRM

Referência de uso para quem opera o CRM por script — inclusive agentes de IA com a chave de API. Cada exemplo desta página foi executado contra a instalação real antes de ser escrito; o que está aqui é o que a API de fato responde, não o que deveria responder.

Endereços e versão

Duas instalações, mesma API. A de desenvolvimento existe para você errar à vontade — ela não fala com o WhatsApp de ninguém.

AmbienteBaseUso
Produção https://evocrm-api.gruporugido.com/api/v1 Atendimento real das clínicas.
Desenvolvimento https://evocrm-api-dev.rugido.com/api/v1 Canais desarmados, nenhuma instância de WhatsApp conectada. Teste aqui primeiro.

Há também um caminho público, /public/api/v1, que não pede autenticação e serve para o widget de chat e para canais do tipo API receberem mensagens de fora. Ele é tratado na seção do canal de API.

Autenticação

Três formas, avaliadas nesta ordem: token de serviço, Authorization: Bearer e api_access_token. Para script e agente de IA, use a terceira — as outras duas expiram.

A chave de API

A chave é um registro em access_tokens que pertence a um usuário. Isso não é detalhe de implementação: é o que define tudo que a chave pode fazer. Ela herda o papel do usuário e, se ele pertencer a um cliente, herda o workspace dele também. 

# toda chamada leva este cabeçalho
curl https://evocrm-api.gruporugido.com/api/v1/workspaces \
  -H "api_access_token: 3f611fbe7258ce52018a2e4fa666dded…"

Sem cabeçalho nenhum a resposta é 401. Com uma chave válida mas sem a permissão da ação, é 403 — a mensagem diz qual das duas coisas faltou.

Emitir uma chave

Pela interface, em Configurações → Tokens de acesso. Por API, o endpoint é do serviço de autenticação e devolve o token em claro uma única vez — guarde na hora. 

curl -X POST https://evocrm-api.gruporugido.com/api/v1/access_tokens \
  -H "Authorization: Bearer $JWT" \
  -H "Content-Type: application/json" \
  -d '{
    "name":   "claude-code-provisionamento",
    "scopes": "inboxes.read inboxes.create agent_bots.create"
  }'

# → data.access_token.token: "d3263c338829a558…"

name e scopes são obrigatórios — scopes em branco devolve 422.

scopes não restringe nada

O campo é obrigatório e fica gravado, mas o CRM nunca o consulta: existe has_permission_scope? no modelo e nenhuma chamada a ele em todo o código. Verificado — uma chave criada com "inboxes.read" lê contatos e conversas normalmente.

Uma chave alcança tudo que o dono dela alcança. Se você precisa de acesso estreito, o caminho é criar um usuário com o papel certo e emitir a chave nele — não confie no campo de escopo.

Login com usuário e senha

Para uso interativo, POST /auth/login devolve um JWT de 8 horas em data.token.access_token, que vai em Authorization: Bearer. Serve para explorar; não serve para automação que roda sozinha.

Envelope de resposta

Toda resposta da /api/v1 vem embrulhada. Sucesso:

{
  "success": true,
  "data": { /* o recurso, ou uma lista */ },
  "meta": { "timestamp": "2026-08-06T13:20:52Z" },
  "message": "Agent bot configured successfully"
}

Erro de validação — repare que os detalhes vêm por campo, prontos para o agente corrigir e repetir:

{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Validation failed",
    "details": [{
      "field": "agent_bot_id",
      "messages": ["pertence a outro workspace e nao pode atender esta caixa"]
    }]
  },
  "meta": { "path": "/api/v1/inboxes/…/set_agent_bot", "method": "POST" }
}
CódigoQuandoO que fazer
401Sem chave, ou chave inválidaConfira o cabeçalho api_access_token.
403Chave válida, papel sem a permissãoA ação exige outro papel. Não insista com outra rota.
404Não existe ou é de outro workspaceOs dois casos respondem igual, de propósito.
422ValidaçãoLeia error.details; o campo culpado vem nomeado.

Paginação em listas: page e pageSize na query (padrão 20), com o total em meta.pagination.total. page_size e per_page também são aceitos.

Workspaces

Cada cliente do Grupo Rugido é um workspace. Canais, contatos, agentes, automações, funis, etiquetas, respostas rápidas e times pertencem a um — ou a nenhum, e aí são globais, nossos, visíveis para todos.

Em toda chamada existe um workspace ativo, resolvido nesta ordem:

  1. A chave é de um usuário de cliente → o workspace é o dele, e ponto. Cabeçalho e corpo são ignorados.
  2. A chave é de um admin → vale workspace_id no corpo; na falta dele, o cabeçalho X-Workspace-Id; na falta dos dois, nenhum — o recurso nasce global.

A chave do cliente não sai do cliente. Verificado: uma chave do Oral Riso mandou X-Workspace-Id e workspace_id apontando para a Cicatriclinic, e o registro caiu no Oral Riso assim mesmo. É a garantia que sustenta entregar chave para colaborador ou agente que atende um cliente só.

Endpoints

# os workspaces que esta chave enxerga
# admin: todos · cliente: só o dele
GET  /api/v1/workspaces

# o workspace ativo desta requisição
GET  /api/v1/workspaces/current

POST  /api/v1/workspaces          # só admin
PATCH /api/v1/workspaces/:id      # só admin

Receita · cadastrar um cliente

O primeiro passo de qualquer provisionamento. O slug é derivado do nome quando omitido. 

curl -X POST https://evocrm-api.gruporugido.com/api/v1/workspaces \
  -H "api_access_token: $CHAVE" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Clínica Nova",
    "logo_url": "https://…/logo.png"
  }'

# → 201  data: { "id": "cc42aa2b-…", "slug": "clinica-nova" }

Guarde o id: ele é o workspace_id de tudo que você criar em seguida.

Receita · canal de WhatsApp oficial

Este é o caso que só existe por API: a interface não conecta WhatsApp oficial sem o SDK de um aplicativo Tech Provider. Pela API, funciona. 

curl -X POST https://evocrm-api.gruporugido.com/api/v1/inboxes \
  -H "api_access_token: $CHAVE" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Clínica Nova — WhatsApp",
    "workspace_id": "cc42aa2b-…",
    "channel": {
      "type": "whatsapp",
      "phone_number": "+5511999990000",
      "provider": "whatsapp_cloud",
      "provider_config": {
        "api_key": "EAAG…",
        "phone_number_id": "111111111111111",
        "waba_id": "222222222222222"
      }
    }
  }'

Os campos ficam na raiz, não dentro de inbox

{"name": …, "channel": …} funciona. {"inbox": {"name": …}} devolve erro sem mensagem útil, porque o controlador lê os parâmetros do nível raiz e não acha o canal. Verificado nos dois formatos.

A credencial é validada na hora, contra a Meta

O EvoCRM chama graph.facebook.com/{waba_id}/message_templates durante o create. Credencial errada não cria canal quebrado: devolve 422 com "Provider config Invalid Credentials". Se você recebeu isso, o problema está no token da Meta ou no waba_id — não no formato do JSON.

provider aceita whatsapp_cloud (oficial), evolution e evolution_go (não oficiais, por QR), baileys, notificame, zapi e default. channel.type aceita whatsapp, api, web_widget, email, telegram, line, sms e sendgrid.

A resposta traz workspace_id, então dá para conferir na hora em qual cliente o canal caiu — sem ir ao banco.

Receita · canal de API

Um canal do tipo api não fala com rede social nenhuma: ele recebe mensagens por HTTP. É o jeito de testar um agente sem envolver WhatsApp, e de plugar um sistema próprio. 

POST /api/v1/inboxes
{ "name": "Canal de testes", "workspace_id": "…",
  "channel": { "type": "api" } }

A resposta traz um identifier no canal. Com ele, o caminho público aceita mensagens sem autenticação — três chamadas, nesta ordem: 

# 1. o contato (você escolhe o source_id e reusa depois)
POST /public/api/v1/inboxes/{identifier}/contacts
{ "source_id": "paciente-42", "name": "Maria" }

# 2. a conversa
POST /public/api/v1/inboxes/{identifier}/contacts/paciente-42/conversations
{}

# 3. a mensagem (aceita id, uuid ou display_id da conversa)
POST /public/api/v1/inboxes/{identifier}/contacts/paciente-42/conversations/395/messages
{ "content": "Quero marcar uma avaliação" }

O caminho público responde 204 com corpo vazio

Os três endpoints acima criam o registro e devolvem corpo vazio. Não trate isso como falha e não tente extrair o id da resposta — não vem. Mande o source_id que você mesmo escolheu e consulte a conversa depois, se precisar do identificador.

Receita · agente de IA

São dois passos: criar o agente e ligá-lo ao canal.

Criar

POST /api/v1/agent_bots
{
  "name": "Agente Clínica Nova",
  "outgoing_url": "https://n8n.exemplo.com/webhook/clinica-nova",
  "workspace_id": "cc42aa2b-…",
  "debounce_time": 3,
  "text_segmentation_enabled": true
}

Ligar ao canal

POST /api/v1/inboxes/{inbox_id}/set_agent_bot
{ "agent_bot_id": "3df714c6-…" }

set_agent_bot substitui, não acumula

Um canal tem um agente. Chamar de novo com outro agent_bot_id troca o vínculo anterior em silêncio. Se você quer conferir o que está ligado, use GET /api/v1/inboxes/{id}/agent_bot.

Agente de um cliente não atende o canal de outro

A tentativa volta 422 com "pertence a outro workspace e nao pode atender esta caixa". Agente global (sem workspace_id) entra em qualquer canal — é assim que um agente compartilhado nosso funciona.

O que o agente recebe

Quando chega mensagem, o EvoCRM faz POST na outgoing_url com um envelope JSON-RPC no formato A2A. O que interessa está em params.metadata: 

{
  "jsonrpc": "2.0",
  "method": "message/send",
  "params": {
    "contextId": "7aea2480-…",      // uuid da conversa = a sessão
    "userId":    "360f177a-…",      // id do contato
    "message": { "role": "user",
                  "parts": [{ "type": "text", "text": "Quanto custa?" }] },
    "metadata": {
      "agent_bot_id": "…", "inboxId": "…",
      "contact": { /* nome, telefone, atributos, etiquetas */ },
      "evoai_crm_data": { "conversation": { "display_id": 395 },
                          "inbox": { "id": "…", "name": "…" },
                          "event": "message_created" }
    }
  }
}

O payload não diz de qual cliente é

Não há workspace_id no envelope — só inboxId. Um fluxo n8n que atende mais de uma clínica precisa manter o mapa de canal para cliente à mão. Abriu canal novo e esqueceu de atualizar o mapa? O agente responde com a base da clínica errada, e o CRM não tem como perceber. Um fluxo por cliente é o arranjo seguro enquanto isso.

Mensagem de atendente humano e mensagem do próprio agente não são entregues ao agente — verificado. É o que impede o eco e o que sustenta a intervenção humana.

Receita · automação

Uma regra tem gatilho (event_name), condições e ações. A regra roda apenas nos eventos do próprio workspace; regra sem workspace_id roda para todos os clientes. 

POST /api/v1/automation_rules
{
  "name": "Pausar IA quando o atendente responde",
  "event_name": "message_created",
  "active": true,
  "workspace_id": "cc42aa2b-…",
  "conditions": [{
    "attribute_key":   "sender_type",
    "filter_operator": "equal_to",
    "values":          ["user"],
    "query_operator":  null
  }],
  "actions": [{ "action_name": "add_label", "action_params": ["agente-off"] }]
}

Gatilhos

message_created, conversation_created, conversation_updated, conversation_status_changed, contact_created, contact_updated.

Condições

SobreChaves
Mensagemcontent, message_type, sender_type
Conversastatus, assignee_id, team_id, inbox_id, labels, priority, conversation_language, mail_subject, browser_language, referer
Contatoname, email, phone_number, identifier, city, country_code, company, blocked
Funilpipeline_id, pipeline_stage_id

sender_type só aceita valores minúsculos

Use "user" para atendente humano e "agentbot" para agente de IA — nunca "User" ou "AgentBot". A consulta envolve a coluna em LOWER(), mas o valor que você manda só é rebaixado quando a chave é content. Com maiúscula a regra salva, fica ativa e nunca casa — o pior tipo de falha, porque é silenciosa.

Ações

send_message, send_canned_response, send_template, send_attachment, add_label, remove_label, assign_agent, assign_team, change_status, change_priority, resolve_conversation, snooze_conversation, mute_conversation, send_webhook_event, send_email_to_team, send_email_transcript, assign_to_pipeline, update_pipeline_stage, create_pipeline_task, update_custom_attribute.

Receita · movimentar conversa

# responder
POST /api/v1/conversations/{id}/messages
{ "content": "Bom dia!", "message_type": "outgoing" }

# mudar o status: open · resolved · pending · snoozed
POST /api/v1/conversations/{id}/toggle_status
{ "status": "open" }

# atribuir a um atendente (ou "team_id" para um time)
POST /api/v1/conversations/{id}/assignments
{ "assignee_id": "…" }

# devolver para o agente de IA
POST /api/v1/conversations/{id}/return_to_bot

# etiquetar
POST /api/v1/conversations/{id}/labels
{ "labels": ["retorno", "orcamento-enviado"] }

return_to_bot falha com "inbox has no agent bot connected" se o canal não tiver agente ativo. Lembre que status ativo no vínculo é 0, não 1.

Receita · movimentar o funil

PATCH /api/v1/pipelines/{pipeline_id}/pipeline_items/{item_id}/move_to_stage
{ "new_stage_id": "95e835dd-…", "notes": "paciente confirmou" }

O parâmetro é new_stage_id

Não pipeline_stage_id, nem stage_id. Errar o nome devolve 404 "Stage not found in this pipeline" — mensagem que induz a procurar o problema na etapa, quando ele está no nome do campo.

Para mover vários de uma vez, PATCH …/pipeline_items/bulk_move.

Receita · contatos

POST /api/v1/contacts
{ "name": "Maria Souza", "phone_number": "+5511987654321",
  "workspace_id": "cc42aa2b-…" }

O mesmo telefone pode existir em dois clientes: são registros independentes, um por workspace. Isso é de propósito — um paciente que fala com duas clínicas não vira um contato só, com o histórico das duas à vista de ambas.
